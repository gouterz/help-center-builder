# Docs platform notes

Read only the section for the founder's platform. Platforms change their syntax from time to time, so check a few existing pages in the repo first. When this file and the repo disagree, the repo wins. These notes were checked against each platform's official docs in September 2026.

## Identify the platform

| File in the docs repo | Platform |
| --- | --- |
| `SUMMARY.md` (often with `.gitbook.yaml` and `.gitbook/assets/`) | GitBook (Git Sync) |
| `docs.json`, or the older `mint.json` | Mintlify |
| `docusaurus.config.js` or `.ts`, and `sidebars.js` or `.ts` | Docusaurus |
| `_meta.js` or `_meta.ts` files next to pages | Nextra |
| `docs/<category>/` folders with `_order.yaml` | ReadMe |
| No repo at all | Hosted help center (Intercom, Zendesk, Help Scout, Notion...) |

## GitBook (Git Sync)

- **Table of contents:** `SUMMARY.md`.
  - `## Heading` starts a sidebar group.
  - List pages as `* [Title](folder/page.md)`, and indent child pages under their parent.
  - Each file can appear only once.
  - `[Title](page.md "Sidebar label")` gives a page a shorter sidebar label.
  - `.gitbook.yaml` can move the root folder and set up redirects.
- **Frontmatter:** `description` becomes the page subtitle and meta description. `icon` takes a Font Awesome name, such as `book-open`. `hidden: true` keeps a page out of the sidebar. The page title comes from the `# H1`. Unquoted colons in frontmatter fail silently, so quote any value that contains one.
- **Emoji icons:** GitBook's docs don't describe how emoji icons are stored. In practice, GitBook exports and reads an emoji icon as the first character of both the H1 (`# 🔔 How to…`) and the `SUMMARY.md` link text. If existing pages already work this way, follow the same pattern. Use pictographic emoji: symbol-range characters (enclosed letters, arrows, media-control symbols) may not be recognised. Keep the `SUMMARY.md` title identical to the H1.
- **Callouts:**

  ```
  {% hint style="info" %}
  …
  {% endhint %}
  ```

  The styles are `info`, `success`, `warning` and `danger`.
- **Images:** files go in `.gitbook/assets/`, up to 100MB each. Use this markup:

  ```
  <figure><img src="../.gitbook/assets/x.png" alt="…"><figcaption><p>…</p></figcaption></figure>
  ```

  Adjust the `../` to the page's folder depth.
- **Preview:** there is no local dev server. GitHub pull requests get a preview link, but only for a published site that isn't behind sign-in. Previews for GitLab merge requests aren't documented. For GitLab, or anywhere a preview isn't available, build one with `scripts/build_review.py` before merging.
- **Publishing:** a commit to the synced branch updates the live site automatically. Branch protection has to let the GitBook app push.
- **URLs:** they follow the table of contents. Pages inside a group can be served at `/<group-slug>/<page>`, not at their folder path, so open the live URL after publishing and check it. Don't change a space's `key`, because that breaks its links.

## Mintlify

- **Table of contents:** `docs.json` at the repo root. `mint.json` is deprecated, and `mint dev` converts it. `navigation` holds tabs and groups, and each group has a `pages` list of paths without the extension:

  ```json
  "navigation": {"tabs": [{"tab": "Guides", "groups": [{"group": "Settings", "pages": ["settings/reminders"]}]}]}
  ```

  Pages left out of the navigation are hidden from the sidebar but still reachable by URL.
- **Frontmatter:** `title` (it's the page heading, so don't add an H1), `description`, `sidebarTitle`, `icon`, `tag`, `hidden` and `noindex`. Icon names come from the project's `icons.library`: Font Awesome by default, or Lucide or Tabler. A single emoji also works.
- **Callouts:** `<Note>`, `<Tip>`, `<Info>`, `<Warning>`, `<Check>` and `<Danger>`. For steps, use `<Steps>` containing `<Step title="…">` blocks.
- **Images:** use root-relative paths only (`/images/x.png`), not `./relative` ones, up to 20MB each. For a caption, use `<Frame caption="…"><img src="/images/x.png" alt="…" /></Frame>`.
- **Preview:** install with `npm i -g mint` (not the old `mintlify` package), then run `mint dev` (it needs Node 20.17+). `mint broken-links` checks links. Pull and merge request previews need a paid plan and work with GitHub, GitLab and Bitbucket. Pull requests from forks don't get previews.
- **Publishing:** pushing to the deploy branch deploys automatically.

## Docusaurus

- **Table of contents:** either `sidebars.js` or `.ts`, or an autogenerated sidebar with a `_category_.json` in each folder (`label`, `position`).
- **Frontmatter:** `title`, `description` (meta and og description), `sidebar_label`, `sidebar_position` and `slug`.
- **Callouts:** `:::note`, `:::tip`, `:::info`, `:::warning` and `:::danger`, each closed with `:::`. Add a title as `:::note[Title]`. Leave blank lines around them, or Prettier can break them.
- **Images:**
  - Next to the page: `![alt](./img/x.png)`.
  - In `static/img/`: `/img/x.png`.
  - There's no built-in figure-with-caption component, so put the caption in italics under the image.
- **Icons:** no built-in page icons. Skip them unless the site already has a custom setup.
- **Preview:** run `npm run start`, or `npm run build` to catch broken links.
- **Publishing:** whatever the host does: Vercel and Netlify give pull-request previews and deploy on merge.

## Nextra

- **Table of contents:** a `_meta.js` or `.ts` file in each folder exports the page order and titles, for example `{ index: 'Home', reminders: 'Reminder emails' }`. Pages that aren't listed are added alphabetically at the end.
- **Frontmatter:** `title` and `sidebarTitle`.
- **Callouts:** `<Callout type="info|warning|error">` from `nextra/components`. There's no "danger" type, so use `error`. For steps, wrap `###` headings in `<Steps>`.
- **Images:** files in `public/`, referenced as `/x.png`.
- **Icons:** no icon field. An emoji at the start of `sidebarTitle` works.
- **Preview and publishing:** it's a Next.js app, so use its dev script and the host's deploy, usually Vercel.

## ReadMe

- **Sync:**
  - With bi-directional git sync (GitHub, GitLab or Bitbucket), merging publishes. Branch names must match ReadMe version names.
  - For a one-way push, use `rdme docs upload`.
- **Structure:** `docs/<category>/` folders, each with an `_order.yaml` listing page slugs. A page with subpages uses `index.md`.
- **Frontmatter:** `title`, `excerpt`, `hidden` and `icon` (Font Awesome classes). Create new pages with `hidden: true` so they stay unpublished until the founder reviews them.
- **Callouts:** a blockquote that starts with an emoji: `> 📘 Title` for info, `> 🚧` for warning, `> ❗️` for danger.

## Hosted help centers (Intercom, Zendesk, Help Scout, Notion)

Write each page as markdown locally, plus a folder of images, and build the review preview from those files. The founder can paste the pages into the editor. If the founder asks, you can create **unpublished drafts** through the API instead:

- **Intercom:** `POST https://api.intercom.io/articles` with `title`, `author_id` and `body` (HTML). `state` defaults to `draft`. There's no image upload: use public image URLs, which Intercom copies to its own hosting.
- **Zendesk:** `POST /api/v2/help_center/sections/{section_id}/articles` with `"draft": true` and `notify_subscribers: false`. To add images, request an upload URL, upload the file, register it with `POST /api/v2/guide/medias`, then reference the URL that comes back.
- **Help Scout Docs:** `POST https://docsapi.helpscout.net/v1/articles` with `collectionId`, `name`, `text` and `"status": "notpublished"`. Images upload to `/v1/assets/article` and need the article's ID, so create the draft first and then add the image links.

Never publish through the API. Leave the drafts for the founder.
